# Change communication

**State the change and its user impact without hiding release facts.**

This profile covers commit subjects, merge-request descriptions and release or
deploy messages. Follow the project's required commit convention, tracker
references and release process. Do not rewrite published history to improve old
wording.

## Keep the source and sink separate

A commit subject is plain text. Store literal UTF-8 text, not Markdown, HTML,
JSON escapes or Telegram entities. Do not pre-escape a subject for a future
notification.

An MR body is Markdown. Use Markdown only where it improves scanning. A Telegram
message is rendered HTML when that sender uses Telegram HTML parse mode. Format
for the sink once, at the final output boundary:

- Keep source strings literal and preserve them verbatim in diagnostics.
- Escape dynamic text and link attributes once for Telegram HTML. Keep an
  apostrophe literal or use the numeric `&#39;`; never use a named apostrophe entity.
- Serialize the final API payload with a JSON serializer. JSON serialization is
  separate from HTML escaping and is not a second text transformation.
- Do not decode, trim, normalize or truncate a diagnostic string in a way that
  changes its meaning. Do not impose an arbitrary subject limit that removes
  essential meaning.

## Write the right artifact

### Commit subject: plain text

Prefer a short, meaningful subject that says what changed and why it matters.
Keep a project-required Conventional Commit prefix when applicable. Use a body
for material tests, limitations, migration notes or non-obvious context.

Before:

```text
fix: fix issue
```

After:

```text
fix(events): prevent localized village page crashes
```

This is illustrative. Confirm the actual cause and scope before using comparable
wording in a commit.

Avoid vague subjects such as `fix bug`, `updates`, `merge main`, or a raw merge
branch subject. The default merge branch subject records Git history; it is not
a human change description.

### Merge-request description: Markdown

Describe the user-facing change, then add tests or limitations only when they
help review. Headings are optional; do not add empty `Summary`, `Testing` or
`Deployment` sections as filler.

Before:

```markdown
## Summary
Fixed stuff.

## Testing
N/A
```

After:

```markdown
Fix localized event-page errors for events without a localized city.

Tests: `<actual command and result>`.
Not deployed.
```

Replace the placeholder with the real command and result, or state why it was
not run. Do not claim that the illustrative incident has been tested or
deployed merely because this profile uses it as an example.

### Deploy message: rendered Telegram HTML

Build a deploy message from verified release metadata: the target, exact
candidate or change description, result, and relevant pipeline or details link.
Do not derive the human description from the default merge subject. A successful
pipeline alone does not prove a deploy; say `deployed` only after the release
workflow verifies it.

Illustrative rendered text (labels and links are examples, not a release claim):

```text
🚚 ✅ 🏁 example.app · prevent localized event-page errors · pipeline
```

Its Telegram HTML source may be:

```html
🚚 ✅ 🏁 <a href="https://example.app">example.app</a> · prevent localized event-page errors · <a href="https://gitlab.example/pipeline/123">pipeline</a>
```

Escape only dynamic values when constructing that HTML. For example, a literal
subject `fix user's event title & city` remains literal in storage and becomes
`fix user's event title &amp; city` only inside the Telegram HTML text node. Keep
the apostrophe literal or use `&#39;`, never a named apostrophe entity.

## Release check

Before sending a release message, verify the real metadata and make the wording
match it:

- Name the actual target and outcome; include failure impact when known.
- Use the verified change description, not an autogenerated merge label.
- Include a useful details or pipeline link when available.
- State `not deployed`, `deployment failed`, or `production unchanged` when
  those are the facts.
- Preserve exact technical strings in logs and diagnostics; summarize them only
  in the human-facing line when the summary remains accurate.
