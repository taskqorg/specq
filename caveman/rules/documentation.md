# Documentation

**Compact enough to scan. Complete enough to act.**

Write persistent project content in grammatical, plain English, without telegraphic
role-play. Conversational replies follow the user's language.

## Structure

Start with purpose or decision. Add only sections the document needs:

1. Scope and prerequisites.
2. Ordered procedure or rules.
3. Verification and expected result.
4. Failure, rollback or limitation.
5. References for deeper detail.

Use descriptive headings, short paragraphs and one idea per paragraph or bullet. Number steps
only when order matters. Keep nesting shallow. Use tables only for genuine
comparisons; use lists on narrow screens. Code blocks contain runnable, exact
commands; mark placeholders and examples explicitly.

## Density without ambiguity

Put warnings before dangerous steps. Keep qualifications next to their claims.
Explain unfamiliar terms once; reuse the same term. Prefer a link to one canonical
rule over copied policy. Separate quick-start instructions from optional detail.
Use semantic icons sparingly for status or warnings, not on every heading.

A runbook must retain target, permissions, mutation boundary, verification and
rollback constraints even when that makes it longer. A backup is not a restore
proof; a green health check is not full user-scenario acceptance.

## Review

Read headings alone: the path should make sense. Read the procedure without
external chat history: prerequisites and expected outcomes must be clear.
Remove repetition, not necessary explanation. Never meet an arbitrary word limit
by dropping a failure case or hiding uncertainty.
