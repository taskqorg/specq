# Merge-request and release messages

Extends [Change communication](changes.md) for merge-request descriptions and
release or deploy messages. Every before/after pair and rendered sample below is
invented (one localized event-page incident), not a change, test or release
claim. Confirm the actual cause and scope; replace each placeholder with the real
command and result, or state why it was not run.

## Merge-request description: Markdown

Describe the user-facing change, then add tests or limitations only when they
help review. Headings are optional; no empty `Summary`, `Testing` or
`Deployment` filler.

For a risky change, state affected users or systems, whether it is reversible,
the rollback action and what rollback cannot restore, with before/after evidence
per [verification](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#run-policy-by-stage).
A sentence or an existing evidence link is enough; routine changes need no risk
section. Green CI does not establish reversibility.

Before:

```markdown
## Summary
Fixed stuff.

## Testing
N/A
```

After:

```markdown
Fix localized event-page errors for events without a localized city.

Tests: `<actual command and result>`.
Not deployed.
```

## Deploy message: rendered Telegram HTML

Build a deploy message from verified release metadata: target, exact candidate
or change description, result, and pipeline or details link. Do not derive the
human description from the default merge subject. A green pipeline alone does
not prove a deploy; say `deployed` only after the release workflow verifies it.

Rendered text:

```text
🚚 ✅ 🏁 example.app · prevent localized event-page errors · pipeline
```

Its Telegram HTML source may be:

```html
🚚 ✅ 🏁 <a href="https://example.app">example.app</a> · prevent localized event-page errors · <a href="https://gitlab.example/pipeline/123">pipeline</a>
```

Escape only dynamic values, once, per [source and sink](changes.md#keep-the-source-and-sink-separate):
a literal subject `fix user's event title & city` stays literal in storage and
becomes `fix user's event title &amp; city` only inside the Telegram HTML text node.

## Release check

Before sending a release message, verify the real metadata and match the wording
to it:

- Name the actual target and outcome; include failure impact when known.
- Use the verified change description, not an autogenerated merge label.
- Include a details or pipeline link when available.
- State `not deployed`, `deployment failed` or `production unchanged` when
  those are the facts.
- Preserve exact technical strings in logs and diagnostics; summarize only in
  the human-facing line, and only while the summary stays accurate.

Operational-message grammar: [Notifications](notifications.md). Integration
boundaries: [Notification adoption scope](../audits/notification-scope.md).
